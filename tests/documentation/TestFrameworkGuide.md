**Use descriptive test names** that explain what is being tested\n3. **Follow AAA pattern**: Arrange, Act, Assert\n4. **Test one thing per test** - keep tests focused\n5. **Use data-driven tests** for multiple input scenarios\n\n### Test Data\n\n1. **Use realistic test data** when possible\n2. **Test with edge cases** (null, undefined, empty, boundary values)\n3. **Clean up test data** after each test\n4. **Use factories** for consistent test data generation\n\n### Assertions\n\n1. **Use specific assertions** (toEqual vs toBe vs toMatchObject)\n2. **Include meaningful error messages** in custom matchers\n3. **Test both positive and negative cases**\n4. **Verify side effects** (state changes, function calls)\n\n### Performance\n\n1. **Keep tests fast** - aim for <1 second per test\n2. **Use mocks** to avoid slow external dependencies\n3. **Run expensive tests** in separate suites\n4. **Parallelize test execution** where possible\n\n### Maintenance\n\n1. **Keep tests up to date** with code changes\n2. **Refactor test code** like production code\n3. **Remove obsolete tests** when features change\n4. **Document complex test scenarios**\n\n## Troubleshooting\n\n### Common
