# Story 1.28: Asset Browser and File Format Synchronization

## Status
Draft

## Story
**As a** development team member,
**I want** clear, consistent standards for asset browser implementation and file formats,
**so that** all agents and developers create compatible, properly functioning assets without conflicts or misunderstandings

## Acceptance Criteria
1. Document and enforce consistent PSG file format structure for fragments
2. Establish clear guidelines for node type naming conventions (camelCase vs PascalCase)
3. Define standard for region/bounding box creation in fragment files
4. Create validation rules for PSG to PSGLib conversion
5. Ensure all agents understand the difference between fragments and full graphs
6. Standardize port definitions and connection handle specifications
7. Document the expected behavior for collapsible regions
8. Create automated validation for asset files before they're added to the library
9. Design extensible node type registry system for future compatibility
10. Establish versioning strategy for file formats to handle evolution
11. Create plugin architecture for custom node types without breaking core
12. Build a central Node Catalog as single source of truth for all available nodes

### Format Specifications Summary
**PSG Format (Fragments):**
- Used for reusable component groups
- Contains nodes, edges, and regions
- Should not include Output nodes in fragments
- Uses x/y coordinates for positioning

**PSGLib Format (Presets):**
- Used for complete importable graphs
- Contains full graph structure with metadata
- Includes usage statistics and marketplace fields
- Uses position objects with x/y properties

### Future Compatibility Design
**Node Type Registry:**
- Centralized registry at `/packages/core/runtime/nodeRegistry.ts`
- Each node type implements `INodeType` interface
- Registration happens at startup or dynamically
- Discovery through decorators or manifest files
- Validation ensures required methods/properties

**Versioning Strategy:**
- PSG format: Major.Minor.Patch (e.g., 1.2.0)
- Breaking changes increment Major
- New features increment Minor
- Bug fixes increment Patch
- Migration tools handle version upgrades

**Plugin Architecture:**
```typescript
interface INodePlugin {
  id: string;
  version: string;
  nodeTypes: INodeType[];
  initialize(): Promise<void>;
  validate(): boolean;
}
```

**Backwards Compatibility Rules:**
- New node types must not break existing graphs
- Unknown node types gracefully degrade
- Version negotiation during import/export
- Legacy format support for 2 major versions

### Central Node Catalog Design
**Node Catalog Structure:**
```typescript
interface NodeCatalog {
  version: string;
  lastUpdated: Date;
  nodes: NodeDefinition[];
  categories: NodeCategory[];
  compatibility: CompatibilityMatrix;
}

interface NodeDefinition {
  id: string;                    // e.g., "weightedChoice"
  displayName: string;            // e.g., "Weighted Choice"
  category: string;               // e.g., "branching"
  version: string;                // e.g., "1.0.0"
  description: string;
  inputs: PortDefinition[];
  outputs: PortDefinition[];
  configuration: ConfigSchema;
  examples: Example[];
  tags: string[];
  deprecated?: boolean;
  replacedBy?: string;
}
```

**Catalog Access Points:**
- REST API: `/api/catalog/nodes` - for runtime queries
- Generated JSON: `/catalog/nodes.json` - for static access
- TypeScript types: `/types/catalog.d.ts` - for development
- Markdown docs: `/docs/node-catalog.md` - for humans
- Agent endpoint: `/api/catalog/agent` - optimized for AI agents

**Auto-Discovery Features:**
- Scan codebase for node implementations
- Extract metadata from decorators/comments
- Generate catalog on build
- Validate against schema
- Check for conflicts and duplicates

### Testing Standards
- Validate all asset files against schemas
- Test PSG to PSGLib conversion with various inputs
- Ensure backwards compatibility with existing assets
- Test with multiple agents creating assets simultaneously

### Specific Test Scenarios
1. **Format Validation Tests**
   - Valid PSG file with regions should convert correctly
   - Invalid PSG file should fail with clear error message
   - Mixed camelCase/PascalCase node types should map correctly
   - Fragment with Output nodes should filter them out

2. **Node Registry Tests**
   - Register new node type and verify in catalog
   - Attempt duplicate registration should fail gracefully
   - Query catalog API for specific node types
   - Test node type discovery from decorators

3. **Version Migration Tests**
   - Load v1.0 file in v2.0 system
   - Auto-migrate old format to new
   - Reject incompatible future versions
   - Test rollback scenarios

4. **Plugin Integration Tests**
   - Load valid plugin manifest
   - Sandbox plugin execution
   - Verify permission restrictions
   - Test plugin node registration

5. **Concurrent Access Tests**
   - Multiple agents creating fragments simultaneously
   - Race condition testing for ID generation
   - Catalog updates during active queries
   - File locking and conflict resolution
